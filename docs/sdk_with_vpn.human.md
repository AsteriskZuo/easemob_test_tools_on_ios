# SDK 实现 VPN 探测的讨论

从几个方面：

1. 是否可以实现(技术层面)
2. 是否可以上架(政策层面)

## 前置澄清：两个问题，不要混为一谈

在讨论 VPN 检测时，始终存在两个独立的问题：

| 问题               | 含义                                                         |
| ------------------ | ------------------------------------------------------------ |
| 是否**设置了** VPN | 系统设置里是否存在 VPN 配置（profile），不管它当前有没有连接 |
| 是否**开启了** VPN | 当前是否有 VPN 隧道正在运行、流量正在经过 VPN 通道           |

这两件事的关系是：

- 开启 VPN 的前提是设置了 VPN
- 但设置了 VPN 不代表开启了 VPN
- **真正的关注点是：是否正在开启 VPN**
- 就算能 100% 确认"设置了 VPN"，但无法确认"正在开启 VPN"，那这个信息没有实际意义

后续所有结论都围绕这个区分展开。

## 实现

### iOS

技术手段：底层 `getifaddrs()` 枚举网络接口，分析 `utun* / ipsec* / ppp*` 等隧道类接口的存在与地址特征。

**探测"是否设置了 VPN"：做不到。**
`getifaddrs()` 只能看到当前正在运行的接口。VPN 配置了但没连接，接口不会出现。`NEVPNManager` 只能读本 App 自己的 VPN 配置，不能枚举系统所有 VPN profile。

**探测"是否已经开启 VPN"：能做高置信度判断，不能 100% 确认。**
当 `utun*` 接口绑定了 `198.18.x.x`、典型私网段等地址时，大概率有第三方 VPN/代理在运行。但 iCloud Private Relay、Wi-Fi Calling 等系统功能也会创建 `utun*` 接口，所以看到 `utun*` 不等于一定是用户 VPN。本质是特征识别，不是系统真值查询。

### Android

技术手段：`ConnectivityManager` + `NetworkCapabilities.TRANSPORT_VPN`。

**探测"是否设置了 VPN"：做不到。**
`ConnectivityManager` 只反映当前网络状态，不读取配置。普通 App 没有权限枚举系统所有 VPN 配置。

**探测"是否已经开启 VPN"：能判断，比 iOS 更直接。**
系统在 `VpnService` 建立隧道时会标记 `TRANSPORT_VPN`，API 直接返回当前活动网络是否走 VPN 传输。对标准 VPN（IKEv2、OpenVPN、WireGuard 等）检出率高。但纯 HTTP/SOCKS 代理不走 `VpnService` 的检测不到。

### 结论

| 能力             | iOS               | Android                 |
| ---------------- | ----------------- | ----------------------- |
| 探测"设置了 VPN" | 不能              | 不能                    |
| 探测"开启了 VPN" | 高置信度，非 100% | 高置信度，比 iOS 更直接 |

两个平台都没有向普通 App 开放"系统级 VPN 状态真值查询"的接口，所以，都不能承诺 100% 准确。

## 上架

### iOS（App Store）

可以上架，但有审核风险。

- `getifaddrs()` 目前没有被禁用
- 风险点不在 API 本身，而在于接口枚举行为可能被理解为环境探测或指纹采集
- 如果用途明确是"网络诊断"，且只做本地判断、不上传明细，风险可控

### Android（Google Play）

可以上架，风险低。

- `ConnectivityManager + NetworkCapabilities` 是官方 API
- 只要用途是网络诊断，且不把结果用于画像、风控、限制用户行为，一般没有明显问题

### 结论

| 平台    | 结论                   |
| ------- | ---------------------- |
| iOS     | 可上架，有一定审核风险 |
| Android | 可上架，风险低         |

## 我的思考

VPN检查 和 即时通讯SDK 放在一起是否合适。放在应用中是否更加合理？

> 我认为放应用里更合理。SDK 的职责是通信，不是诊断网络环境。VPN 检查属于排障辅助能力，和 IM 核心功能无关。放在 SDK 里会让 SDK承担不必要的审核风险——尤其 iOS 端，getifaddrs() 的风险是跟着二进制走的，SDK 集成到哪个 App，风险就带到哪个 App。

除了 VPN ，还有很多方法可以影响 即时通讯SDK 和服务器的连接，例如：代理。

> 影响 SDK 连接的因素很多：HTTP 代理、SOCKS 代理、防火墙规则、DNS 劫持、运营商策略等等。只查 VPN覆盖不了全部场景。如果目的是"快速定位连接失败原因"，更实际的做法是 SDK自身把连接失败的错误码、握手阶段、超时位置这些信息暴露清楚，让应用层或排障工具去做环境判断，而不是 SDK 自己去猜网络环境。
