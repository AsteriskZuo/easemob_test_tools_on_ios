# VPN 检测方案说明

这份说明只回答三个问题：

1. 这个能力能不能做
2. 做到什么程度
3. 上架有没有风险

先把概念说清楚。

VPN 相关其实有两个问题：

- 设备**是否设置了 VPN**
- 设备**是否已经开启 VPN**

这两个问题不能混在一起说。

“已经开启 VPN”才是真正有业务意义的问题。因为设备就算设置过 VPN，只要当前没开，这个信息本身没有实际价值。

下面的结论，都是围绕这两个问题分别说明。

---

## 一、结论先说

### 1. iOS

- **是否设置了 VPN：普通 App 做不到准确判断**
- **是否已经开启 VPN：可以做高置信度判断，但不能做到 100%**
- **上架风险：有，但可控**

### 2. Android

- **是否设置了 VPN：普通 App 做不到准确判断**
- **是否已经开启 VPN：可以判断，方案比 iOS 更直接**
- **上架风险：低**

---

## 二、iOS 这边的实际情况

### 1. 是否设置了 VPN

结论：**普通 App 无法确认。**

原因很简单：

- `getifaddrs()` 只能看到当前正在运行的网络接口
- 如果用户只是“配置了 VPN”，但当前没有连接，对应接口不会处于运行状态
- `NEVPNManager` / `NETunnelProviderManager` 只能读取本 App 自己创建或可见的 VPN 配置，不能拿它去枚举系统里所有 VPN 设置

所以，iOS 上不能把这个能力说成“检查系统有没有设置 VPN”。普通 App 没有这个权限边界外的能力。

### 2. 是否已经开启 VPN

结论：**可以做判断，但本质上是特征识别，不是系统真值查询。**

当前项目里的 iOS 方案，核心是：

- 调用 `getifaddrs()` 枚举接口
- 分析 `utun* / ppp* / tun* / ipsec*` 这类接口
- 再结合接口地址特征做判断

现有实现文件：

- `sdkTest/VPNChecker.swift:198`

这份代码当前已经在做接口枚举，底层调用是：

- `getifaddrs()`：`sdkTest/VPNChecker.swift:211`
- `freeifaddrs()`：`sdkTest/VPNChecker.swift:238`

接口名匹配逻辑在：

- `sdkTest/VPNChecker.swift:180`

真机日志里，已经看到过比较明确的例子：

- `utun7` 上出现 `198.18.0.1`
- 同时还有 `fd00:1234:ffff::10`

这个组合说明，当前确实存在隧道类网络能力在运行，而且从现有分析看，高度疑似是第三方代理/VPN 应用建立的隧道。

但是，这个结论仍然不能表述成“100% 检测到 VPN 已开启”，原因也很明确：

- iOS 系统自己的某些能力也会创建 `utun*` 接口
- 看到 `utun*` 不等于用户一定开启了第三方 VPN
- BSD 接口名本身也不是 Apple 承诺稳定的公开 API

所以，iOS 这边最准确的说法是：

> 可以基于网络接口和地址特征，对“当前是否存在 VPN/代理隧道正在运行”做高置信度判断，但不能做到系统级 100% 确认。

### 3. iOS 上架怎么判断

结论：**能上架，但有审核风险。**

这里要把“API 能不能用”和“审核会不会质疑”分开。

#### 3.1 从 API 本身看

当前使用的是：

- `getifaddrs()`
- `freeifaddrs()`

这两个都是标准 BSD 网络接口 API。到目前为止，没有看到 Apple 明确把它们列为禁止使用的 API。

所以，单从“是否调用了被禁 API”这个角度看，当前方案没有直接违规。

#### 3.2 风险主要在哪里

风险不在 API 名字本身，风险在于：

- 枚举接口名
- 读取 IP 地址
- 读取 flags

这类行为如果处理不当，审核员可能会把它理解成：

- 设备环境探测
- 设备指纹采集
- 非必要网络环境识别

如果 App 的主功能本身和网络诊断没有明显关系，这个风险会更高。

#### 3.3 如果以“网络诊断”为理由

这个理由是说得通的，但前提是实现方式也要和“网络诊断”一致：

- 只在本地判断
- 不上传完整接口列表
- 不持久化保存接口明细
- Release 包不要输出完整接口日志
- 审核备注中明确说明用途是“网络诊断 / 连接问题排查”

只要是按这个方式使用，风险是可控的。

#### 3.4 iOS 上架的实际口径

比较合适的口径是：

> 该能力用于网络诊断，可辅助判断当前网络环境是否存在隧道类连接，从而帮助排查连接异常。

不合适的口径是：

> 检查用户是否开启 VPN
>
> 检查用户设备是否设置 VPN
>
> 检测用户代理环境

后面这种表述更容易被审核放大理解。

## 三、Android 这边的实际情况

### 1. 是否设置了 VPN

结论：**普通 App 也做不到准确判断。**

原因和 iOS 类似。

普通 Android App 能看到的是当前网络状态，不能枚举系统里所有 VPN 配置。除非是企业管控场景、Device Owner、系统级应用，否则不能把这个能力说成“检查设备是否设置过 VPN”。

所以 Android 也一样：

- “是否设置了 VPN”没有实际检测价值
- 就算知道设置过，也不能说明现在正在使用

### 2. 是否已经开启 VPN

结论：**可以判断，而且比 iOS 更直接。**

Android 更适合用系统公开 API 来判断当前活动网络是不是 VPN 网络。

推荐方案是：

- `ConnectivityManager`
- `NetworkCapabilities`
- `hasTransport(NetworkCapabilities.TRANSPORT_VPN)`

这套方式的特点是：

- 是 Android 官方公开 API
- 表达的是当前活动网络的传输类型
- 不需要走底层接口探测
- 比 iOS 上靠 `utun*` 和地址特征分析更直接

另外，接口枚举也能作为辅助信号，例如看：

- `tun0`
- `ppp0`
- `ipsec*`

但 Android 这边更建议把它作为补充，不建议把它当主判断依据。

### 3. Android 工具类实现

我已经补了一份参考实现文档：

- `docs/VPNChecker.kt`

这份实现里有两层判断：

1. 主判断：`ConnectivityManager + NetworkCapabilities.TRANSPORT_VPN`
2. 辅助判断：`NetworkInterface` 枚举 `tun / ppp / tap / ipsec` 接口

返回结果包括：

- `isVPNActive`
- `tunnelInterfaces`
- `summary`

这个实现适合作为 Android 侧的参考工具类。

### 4. Android 上架怎么判断

结论：**风险低，明显低于 iOS。**

原因有几个：

- 使用的是 Android 官方网络状态 API
- 所需权限只是 `ACCESS_NETWORK_STATE`
- 不需要读系统私有信息
- 不需要读 `/proc/net` 这类越来越受限的底层路径
- 不需要触发 `VpnService.prepare()` 这类带交互的行为

也就是说，Android 这边如果采用 `ConnectivityManager + NetworkCapabilities` 方案，本身就是一条比较正常、比较稳妥的实现路线。

Google Play 这边真正需要注意的，主要不是 API 合规性，而是数据使用方式：

- 如果只是本地做网络诊断，风险低
- 如果把结果上传后用于用户画像、风控、限制用户行为，就会带来合规风险
- 如果应用收集了相关状态数据，需要在 Data Safety 里如实说明

Android 这边比较合适的口径同样是：

> 用于网络诊断，判断当前网络环境是否可能经过 VPN 通道，从而辅助分析连接问题。

### 2. 本次讨论形成的最终判断

- iOS 和 Android 都**不能**把能力定义成“检查设备是否设置了 VPN”
- iOS 和 Android 都**可以**对“当前是否存在 VPN/代理隧道正在运行”做判断
- iOS 的判断方式偏特征识别，风险和不确定性更高一些
- Android 的判断方式更直接，工程上更稳妥
- 两个平台都不应该对外承诺“100% 检测 VPN 是否开启”

---

## 五、最后建议

如果只是为了业务判断和排障，建议统一按下面这个口径落地：

### 可以说的

- 检查当前网络环境是否存在隧道类连接
- 辅助判断当前连接异常是否与 VPN/代理有关
- 用于网络诊断

### 不建议说的

- 检查设备是否设置了 VPN
- 100% 检查 VPN 是否开启
- 系统级 VPN 检测
- 检测用户代理行为

### 最终一句话

这个能力可以做，但只能做成“网络诊断中的高置信度识别能力”，不能做成“系统级、100% 准确的 VPN 检测能力”。
